## 1 基本介绍

`rebase` (变基) 的核心功能是 **改变提交历史**;

它会将一系列的提交剪切下来, 然后应用到另一个分支的最新提交上去, 就好像这些提交一开始就是在这个分支上做的一样.

`rebase` 与 `merge` 不同:

- `merge` 会创建一个新的合并提交, 来将两个分支的历史连接起来, 会有一个非常明显的合并点;
- `rebase` 则会把提交一个个应用到目标分支的最新提交上, 重写你的提交历史, 让它看起来是一条直线.

## 2 Rebase 基本工作流

>场景: 你在 `feature` 分支上开发新功能, 同时 `main` 分支上有人提交了更新; 你想让你的分支包含 `main` 分支的最新更新, 让历史记录更清晰.

使用 `merge`:

```bash
git checkout main
git pull                 # 获取最新的 main
git checkout feature
git merge main           # 将 main 合并到 feature
```

会额外产生一个合并提交, 出现 "分叉" 再 "汇合" 的菱形结构;

---

使用 `rebase`:

```bash
git checkout feature
git rebase main          # 将 feature 分支的基础变到 main 的最新提交上
```

其执行的过程是这样的:

1. Git 找到 `feature` 和 `main` 两个分支的共同祖先;
2. 它将 `feature` 自从这个祖先后的所有提交暂存为补丁;
3. 再将 `feature` 分支重置到 `main` 分支的最新提交;
4. 最后, 将刚刚保存的补丁, 按照顺序在这个新基础上重新应用一遍.


## 3 Rebase 的主要模式

### 3.1 标准模式

上面案例中的模式就是标准模式, 它会自动应用提交.

### 3.2 交互模式

```bash
git rebase -i <base>
```

使用上面的命令, 会进入一个交互界面, 允许你在重新应用提交的时候对它们进行编辑.

常用的操作有:

- `pick`: 使用这个提交（默认）.
- `reword`: 使用这个提交, 但修改提交信息.
- `edit`: 使用这个提交, 但暂停 rebase 过程, 允许你修改提交的内容(例如添加漏掉的文件).
  修改后用 `git rebase --continue` 继续.
- `squash`: 将这个提交**压缩**到前一个提交中, 并将它们的提交信息合并.用于将多个小提交合并成一个有意义的提交.
- `fixup`: 类似`squash`, 但会丢弃这个提交的提交信息.
- `drop`: 丢弃这个提交.
